Between v1 and v2 of that script the meaning of a row changed, and the change is load-bearing for anyone reading the table: a row that says OK under v1 and a row that says OK under v2 are not the same claim.
First, whatever the acceptance test found could not have altered the record, because the row had already been written by the time the test ran.
Second, the vocabulary had no slot for anything but a clean run or a hang: a process that exited non-zero for any reason was filed as TIMEOUT, and a process that exited zero was filed as OK regardless of whether the needle ever appeared in the response.
In the worst case a dispatch could produce a row reading OK, written before the test ran, on the strength of a zero exit status and a needle string the dispatcher itself had placed on the wire.
The general point is worth stating for reproducers: any matching test built on hand-typed assumptions about a captured stream should be replaced by fixtures produced by the same code path that produces the stream.
There is no transcript for an echo to satisfy, because there is no echo.
This gate is stricter than v1's whole-transcript search twice over, once because it demands a position and once because it operates on response-only output.
A reproducer who doubts a verdict can move from the row to the retained files and check it by hand.
For counting, this means the instrument holds one row per dispatch that passed the preconditions and reached the gate, and an exit code of 2 from the script is the signature of a precondition failure that produced no row.
One run proves the mechanics, not a track record, and every v1 row in the instrument predates all of the safeguards described above and should be read under v1 rules.
Trust a v2 OK only after opening the retained .out and .err files under the row's per-dispatch key and confirming that, after carriage-return normalisation, the needle is the last non-empty line of the response.
